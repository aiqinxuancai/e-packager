## 修复依据

### 保留原生声明身份和顺序

初始全量编译发现 13 个原件可编译、回包不能编译的样本：93、246、247、316、317、326、327、339、341、342、356、357、383。独立二进制探针证明，仅恢复程序集及方法表的原顺序、保持重新生成的方法体不变，就能恢复代表样本的编译。

原重排来自 `8c7ba37` 的模块导入重建：本地声明提前、导入声明重新分组。该规则能组织新工程，却会改变已有工程的链接位置。现在有原件时按原生 ID 稳定排列程序集、方法、结构和 DLL；新增声明稳定追加，没有原件的新工程沿用既有规则。结构顺序还影响同名类型消歧；`RECT` 被改成带后缀的名称也是重排造成的，不靠修改这个样本的名称解决。

隐藏导入类上的本地方法现在正常导出并语义编码；旧模块类声明也不再被当前外部模块接口无声替换。结构和 DLL 的二进制审计进一步发现遗漏的隐藏历史声明，已从原生声明字段完整恢复，包括已存在的隐藏声明中曾被重新分配的参数 ID、成员 ID 及其类型和布局。只有工程的模块引用身份未变时才保留这部分历史声明；环境搜索得到的 `resolvedPath` 不等于用户更换了模块。可见声明删除及真实模块依赖删除的反向测试均通过。

这里保留的是 ID、声明、类型与布局，不复用旧本地可执行方法体。源码变化后仍强制重新语义编码。`<对象>` 行为未改。

### 统一显示文本和身份摘要

备注空白原先在解析及显示两端都被裁剪。实际 EideCore 原生源码读取确认 IDE 保留这些空白；现在只消耗字段分隔符的一个空格，保留正文、制表符、多行及纯空白续行。

备注正文保留之后，身份摘要仍须和原生快照使用一致的规范化规则。两端摘要不一致曾使未修改的结构、DLL、常量被当作新声明，进而改变长文本资源文件名中的 ID。现在只在身份摘要中统一空白规则，实际数据不裁剪。

同名类/结构的摘要也统一使用导出的消歧名称，回包保留匹配声明的原生名称；同时兼容旧工作区使用原生名计算的摘要。旧工作区双架构测试确认结构 ID 不变。

独立原生读取还证明某些 DLL 入口名末尾确有空格，如 `ShowCursor `。拆包的引号格式化原先删除了这些空格；已改为保留引号内原文，而不是给特定命令添加例外。

### 无接收者的支持库成员命令

`销毁 ()`、`取窗口句柄 ()` 的某些原生调用没有显式对象，但已绑定支持库成员命令。回包原先按全局命令查找失败，降级为未分析文本。现在依据支持库成员分类与原生引用身份解析，显示不变，方法体重新语义编码。

## 验证方法

范围固定为模块目录全部 489 个 `.e` 中的 488 个非空文件；编号 37 为零字节文件。`.ec` 仅作为依赖，不作为测试输入。使用独立副本，原始目录哈希在全量结束时复核。

每个样本执行 Win32/x64 两条流水线：拆包、无修改回包、编辑各页面、语义回包、再拆包、二次回包。除进程退出码外，还检查源内容、资源字节、声明 ID 和顺序、原生源码及历史引用。原件与回包分别编译，只有同轮原件成功而回包失败才记为编译回归。

- `TestEideCoreSourceAudit.py`：以冻结的最新 EideCore 原生源码读取实现独立对照。
- `TestNativeDeclarationOrder.py`：直接解析 `.e` 二进制，检查程序集、方法、结构、DLL 的 ID 丢失、重复及相对顺序。
- `TestNativeHiddenPayloads.py`：直接比较隐藏结构/DLL 的名称、备注、类型、数组、成员/参数 ID 和字段，避免仅检查顶层声明 ID。
- `TestNativeReferenceRoundtrip.py`：检查历史引用是否错绑及是否新增未分析语句。
- `TestNativeCompileAudit.py`：原件和两架构回包的编译、产物验证及诊断对照。
- `TestIdeCompileAudit.py`：真实 IDE 按原生目标编译，并确认实际 EXE/DLL/EC 产物。使用隔离 IDE 和实体私有 `ecom` 目录，避免发布产物复制到安装目录。
- `TestNativeDeclarationRemarks.py`：备注空白、DLL 引号内空白、再次语义编辑后的身份及二次回包稳定性。
- `TestNativeHiddenDeclarations.py`：隐藏结构/DLL 保留，可见声明删除不会被恢复。

二进制及测试源码哈希位于最终目录的 `verification-*-hashes.json`；中间证据不覆盖。`audit-r12-all-e` 因后续重排覆盖原顺序而提前停止；`audit-r13-all-e` / `compile-r13` 发现隐藏声明字段仍会重建后被新版本替代，也提前停止。两轮中间结果均不计入最终统计。

## 原件失败排除与编译诊断修正（续测）

用户明确要求原工程自身失败不计入回包失败。新增 `SummarizeIdeCompileAudit.py` 按原件资格汇总：只有原件明确的编译错误或缺失依赖、且没有其他轮次原件成功证据时，才能排除。单纯超时、启动结果缺失、EideCore 的 `%s%s` 异常不作为排除理由。每个通过项必须有同轮原件、Win32、x64 三方成功，重新核验输入、工具及产物哈希。

本轮发现并修复 AutoLinker 两处误报超时原因：

- 原生 IDE 模块配置错误使用 `错误：`，没有编号。`CompileDiagnostics` 现统一识别全角/半角冒号格式，复用现有诊断及结束等待机制；没有按工程名或错误全文写例外。
- 静默编译 Hook 提前返回，曾漏记缺失模块消息。现将 ANSI/Unicode 消息送入已有无头诊断收集器，已识别的阻断依赖消息会终止产物等待并保留结构化证据。

测试脚本的外层期限也由启动器期限之前调整到之后，避免在启动器写诊断前杀掉它。`ide-v2-native-probe` 的缺依赖原件与双架构回包均快速返回同类失败，正常工程三方仍编译成功；`ide-diagnostics-probe` 同样验证未设置模块名称与正常发布路径。`diagnostics-selftest.json` 包括新错误格式、历史日志不误判以及已有错误位置映射测试，全部通过。`build-AutoLinker-diagnostics-v2.log` 记录 fne_release Win32 构建通过。安装目录未被替换。
